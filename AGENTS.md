Правило "Комментарии".
Пишется полноценный doxygen комментарий.
Не дублировать информацию. Например если в описании параметра сказано, что вектор единичный, не надо писать об это в warning.
Малозначимые блоки лучше не писать. Здесь details, note, warning, todo просто для примера:
В note пишутся дополнительные, малозначимые сведения, например о производительности.
В warning всё что может привести к ошибкам, непредсказуемому поведению.
В todo - какие-то недоделки, которые надо сделать позже.
На разные вещи можно писать несколько блоков note, warning, todo.

/**	@brief Длина ломаной.
    @details
    @note
    @note
    @warning Значения должны быть числовыми.
    @warning
    @todo
    @todo
	@param[in] aPos - массив позиций.
	@return Длина ломаной. */
Val LengthPolyline(const vector<Pos>& aPos);



Правило "Комментарии - return". Лучше чётко прописать значения return.
Не стоит пересказывать/дублировать. Если итак описано, можно максимально кратко:
"Обработанный вектор.", "Повёрнутая Бинормаль" (а не "Бинормаль, повёрнутая вместе с касательным вектором").
Если правила обработки/поворота описаны, говорить о них больше не надо. Пример:

	/**	@brief Проверка вектора на единичность (в пределах погрешности).
		@param[in] v - вектор.
		@return 1 - вектор единичный; 0 - нет. */



Правило "Комментарии - 1 строка". В простых случаях можно написать 1 строчный коментарий. Пример:

/// Ключевая точка сплайна (в 3d).
struct KeySpline
{
	Pos pos;	///< Позиция.
	Vec3 t;		///< tangent / вперёд / ось x / производная нормализованная.
	Vec3 b;		///< binormal / вправо / ось y.
	Val len;	///< Длина отрезка сплайна (после этой точки до следующей).
};



Правило "Комментарии - кратко".
По возможности пишется кратко: не очень сложные вещи, до которых можно додуматся логически, лучше не писать.
Например, если идёт поворот вектора также как другой, то и так понятно что ортогональность сохраняется.



Правило 1. Cборка — scons, а не make/cmake.

Правило 2. Используются определения из BASE_H и META_H. Стиль кода аналогичный.

Правило 3. namespace GEng обычно включён, его не надо писать в каждом выражении.

Правило 4. Все методы, функции, классы - всегда с большой буквы. Переменные всегда с маленькой.

Правило 5. С шабонами glm можно работать так:

	template<length_t L, typename T, qualifier Q>
	GLM_FUNC_QUALIFIER vec<L, T, Q> Normalize(vec<L, T, Q> v)
	{
		if ( GEng::IsApproxZero(v) )
			return vec<L, T, Q>(0);
		return glm::normalize(v);
	}

Правило 6. Почти запрет дублирования кода. Используются шаблоны; маленькие, но универсальные фкнуции и классы.
Но не надо выносить вфункции странные, специфичные методы.Только универсальные.

Правило 7. Общая длина строк всегда не более 80 символов. Надо красиво переносить, если не помещается.

Правило 8. Числа пишутся как есть: "1", "2.1". Без приставок (1.0f), без конструктор типа T(1).

Правило 9. Не нужно писать сложнын строки. Обычно лучше разбить на более простые. 1 логическое действие - одна строка.

Правило "Гибкость". Максимальная гибкость кода. Он может использоватся в непредвиженных случаях, не стоит это пресекать.
Например не нужны проверки ортогональности, если функция просто поворачивает вектор как другой. Может надо будет повернуть именно такие вектора.
